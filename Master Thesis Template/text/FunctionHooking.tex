\chapter{Hooking and Reversing: Core Techniques of Our Cheat Framework}

Following the successful injection of our module and the circumvention of anti-cheat defenses, two tightly integrated techniques become central to the operation of our cheat: \textbf{reverse engineering} and \textbf{function hooking}. These mechanisms allow for in-depth manipulation of game internals, enabling the cheat to operate with both precision and stealth.

Reverse engineering provides the necessary insight into undocumented functions, memory layouts, and internal behaviors of the game engine. Function hooking, in turn, leverages this knowledge to intercept key routines, modify logic at runtime, and inject custom functionalities without breaking the expected control flow of the application.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Function Hooking}} \\
\textit{Function hooking} is the practice of redirecting a function's execution flow to custom code. This technique enables interception, observation, or alteration of program behavior at runtime—without requiring access to the source code.
\end{tcolorbox}

Among the various hooking techniques explored during our implementation, the \textbf{trampoline hook} proved to be the most robust and least intrusive. It allows us to reroute execution to our handler while preserving the original logic and avoiding stability issues that often arise from more aggressive methods.

This chapter provides a focused analysis of trampoline-based interception, its implementation via the \texttt{MinHook} library, and its vital role in achieving stable, persistent in-game modifications that remain hidden from both users and anti-cheat mechanisms.

\section{Reverse Engineering and Function Discovery}

Before any hooking can take place, one must first determine which functions are responsible for the in-game behaviors to be modified.  
This task requires a careful process of reverse engineering—analyzing the game's internal binaries, particularly \texttt{client.dll}, which encapsulates most of the client-side logic.

Using a combination of static analysis tools such as \textit{IDA Pro} and \textit{Ghidra}, along with dynamic debuggers like \textit{x64dbg}, we disassembled code, examined symbols, and traced runtime execution to identify candidate functions for interception.

To bypass Address Space Layout Randomization (ASLR), we extracted \textbf{function signatures}—short, distinctive byte patterns unique to each function.  
Our injected DLL performs runtime pattern scanning to locate these signatures and apply hooks dynamically. This guarantees compatibility across executions and system reboots.

Unlike absolute address targeting, which fails under ASLR, our technique relies on scanning instruction bytes.  
Signatures are constructed with partial wildcards (\texttt{??}) to accommodate variable components like offsets or pointers, which may shift across builds.

For example, the following byte pattern is used to locate the view matrix computation within \texttt{client.dll}:

\begin{lstlisting}[style=cppstyle]
"48 8D ?? ?? ?? ?? ?? 48 C1 E0 06 48 03 C1 C3 CC CC"
\end{lstlisting}

Here, wildcard bytes increase pattern robustness by matching essential instruction sequences while tolerating relocation or minor binary differences.  
The full implementation of our pattern scanning logic resides in the \texttt{helper.cpp} module of our codebase.

\section{Why Trampoline Hooks Are Effective}

Trampoline hooks offer a highly effective mechanism for real-time manipulation of game logic while minimizing the footprint detectable by anti-cheat systems:

\begin{itemize}
  \item They preserve control flow, allowing seamless continuation of the original function after the cheat logic executes.
  \item They maintain stack consistency and valid return addresses, reducing exposure to techniques like return address verification used by VAC.
  \item They avoid allocating and executing new memory pages, lowering the chances of detection by memory scanners.
\end{itemize}

This balance of flexibility, stealth, and resilience makes trampoline hooking the preferred method for runtime code interception in advanced cheat frameworks like ours.

\section{Implementing Hooks with MinHook}

To safely and efficiently intercept internal game functions, we rely on \textbf{MinHook}—a lightweight, open-source library tailored for x86 and x64 Windows systems.  
Following the function discovery and signature matching steps described earlier, MinHook enables us to install trampoline hooks with minimal code and maximal reliability.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: MinHook}} \\
\textit{MinHook} is a minimalistic C/C++ library that simplifies function hooking by handling instruction relocation, trampoline setup, and thread-safe patching. It is widely used in both research and production environments for its efficiency and robustness.
\end{tcolorbox}

Our hook implementation follows a consistent structure:

\begin{itemize}
    \item Define a \texttt{typedef} for the original function’s signature.
    \item Declare a static pointer to store the trampoline (original) function.
    \item Implement a static method to contain the custom cheat logic.
\end{itemize}

\textbf{Example: World Color Modulation Hook}

\begin{lstlisting}[style=cppstyle]
// Class responsible for world color modulation hook
class WorldModulation {
public:
    typedef void* (__fastcall* ModulateWorldColorFn)(...);
    static ModulateWorldColorFn oModulateWorldColor;

    static void* __fastcall hModulateWorldColor(...);
};

WorldModulation m_WorldModulation;
\end{lstlisting}

To install the hook using MinHook:

\begin{lstlisting}[style=cppstyle]
// Function to initialize and install the hook
void InitHook() {
    MH_Initialize(); // Initialize MinHook

    MH_CreateHook((LPVOID)TargetAddress, &WorldModulation::hModulateWorldColor, 
                  (LPVOID*)&WorldModulation::oModulateWorldColor);

    MH_EnableHook((LPVOID)TargetAddress); // Activate the hook
}
\end{lstlisting}

The custom hook modifies behavior only if a specific global flag is active:

\begin{lstlisting}[style=cppstyle]
// Hooked function definition
void* __fastcall WorldModulation::hModulateWorldColor(...) {
    if (!Globals::worldModulation)
        return oModulateWorldColor(...); // Call original if disabled

    for (int i = 0; i < pWorld->count; i++) {
        auto& obj = pWorld->array[i];
        obj.SetColor(Globals::worldModulationColor);
    }

    return oModulateWorldColor(...);
}
\end{lstlisting}

This selective execution strategy ensures that the cheat logic remains unobtrusive, maintaining performance and stability when inactive.

\section{Final Thoughts on Trampoline Hooking}

\textbf{Trampoline hooking} offers a powerful, stealthy, and modular mechanism for real-time manipulation of gameplay logic.  
By preserving control flow, maintaining valid return addresses, and avoiding allocation of suspicious memory regions, it reduces the likelihood of detection by modern anti-cheat systems.

The methodology presented—comprising targeted \textbf{reverse engineering}, dynamic signature scanning, and robust hook deployment via \textbf{MinHook}—constitutes the core of our cheat framework.  
This process has enabled us to identify and intercept internal game functions with precision, even across updates or memory relocations.

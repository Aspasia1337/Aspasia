\chapter{Function Hooking and Trampoline-Based Interception}

\section*{Overview}

At the heart of our cheat framework lies a fundamental and widely-used technique: \textbf{function hooking}. This mechanism allows us to intercept and manipulate internal function calls within the game, modify their behavior, and seamlessly resume execution without disrupting the application’s control flow. Among the various hooking strategies available, the most stable and stealthy is the \textbf{trampoline hook}.

Trampoline hooking offers a reliable and elegant solution for redirecting code execution to custom payloads while preserving the original function’s logic. In this chapter, we present an in-depth explanation of trampoline hooks—how they work, why they are effective, and how they can be implemented safely using the \texttt{MinHook} library.

\section{What is a Trampoline Hook?}

A trampoline hook works by overwriting the beginning of a target function with a jump (typically a near relative JMP or absolute indirect jump) to a custom handler—our hook payload. Since this patch modifies the first few bytes of the original function, those instructions must first be preserved to avoid corrupting the original behavior. We do this by copying them to a new, executable memory region known as the \textit{trampoline}.

Once our custom payload has executed, control is passed to the trampoline, which executes the preserved instructions and then jumps back to the original function, resuming execution as if nothing had changed.

This redirection process involves the following four components:

\begin{enumerate}
  \item \textbf{Original (Hooked) Function} – The function entry point is patched to redirect execution to the relay function.
  \item \textbf{Relay Function} – A lightweight jump stub that forwards execution to the hook payload using a 64-bit jump (on x64).
  \item \textbf{Hook Payload} – Executes custom logic (e.g., cheat functionality), then invokes the trampoline.
  \item \textbf{Trampoline} – Contains the original stolen instructions and ends with a jump back into the body of the original function.
\end{enumerate}

\section{Reverse Engineering and Function Discovery}

Before hooking any function, it is essential to identify the ones responsible for the behaviors we intend to alter. This process involves reverse engineering the game’s dynamic libraries—most notably \texttt{client.dll}, which houses the majority of client-side logic.

Using reverse engineering tools such as \textit{IDA Pro}, \textit{Ghidra}, or \textit{x64dbg}, we analyzed exported symbols, disassembled code, and examined runtime behavior to identify functions of interest. Once located, we extracted their byte-level signatures to ensure our hooks could locate the same functions across multiple game sessions.

To account for memory layout randomization introduced by ASLR (Address Space Layout Randomization), we used these byte patterns as unique \textbf{signatures}—compact sequences of bytes that uniquely identify the beginning of a function. Our injected DLL scans process memory at runtime to locate these signatures and dynamically apply the hook in each session.

\section{Why Trampoline Hooks Are Effective}

Trampoline hooks are particularly effective for real-time game manipulation and evasion of anti-cheat mechanisms due to several key benefits:

\begin{itemize}
  \item They preserve the original control flow, allowing the application to behave as expected after executing the custom payload.
  \item Return address and call stack integrity is maintained, which helps evade return address validation techniques used by anti-cheat engines such as VAC.
  \item No shellcode or foreign code is injected into unfamiliar memory regions, which significantly reduces the risk of detection by memory scanners or heuristic analysis tools.
\end{itemize}

In summary, trampoline hooking strikes a balance between flexibility, stability, and stealth—making it the preferred method in both benign instrumentation tools and game hacking frameworks.


\section{Implementing Hooks with MinHook}

To hook functions safely and efficiently, we use \textbf{MinHook}, a lightweight and open-source x86/x64 API hooking library for Windows.

Before installing the hook, we first define the structure of the original function inside a dedicated class. This class also contains the trampoline pointer and our custom hook implementation. For example:

\begin{lstlisting}[style=cppstyle]
class WorldModulation {
private:
    static ByteColor ColorCache;

public:
    typedef void* (__fastcall* ModulateWorldColorFn)(CAggregateSceneObjectWorld*, void*);
    static ModulateWorldColorFn oModulateWorldColor;
    static void* __fastcall hModulateWorldColor(CAggregateSceneObjectWorld* pAggregateSceneObject, void* a2);
};

WorldModulation m_WorldModulation;
\end{lstlisting}

This setup provides a clean and organized structure where:
\begin{itemize}
  \item We define the function type via a typedef.
  \item We store a pointer to the original (trampoline) function.
  \item We implement our custom hook logic inside a static method.
\end{itemize}

Then we proceed with the actual installation using MinHook:

\begin{lstlisting}[style=cppstyle]
void* __fastcall WorldModulation::hModulateWorldColor(CAggregateSceneObjectWorld* pWorld, void* a2) {
    ByteColor Color = Visual::ToByteColor(Globals::worldModulationColor);

    if (Globals::worldModulation && Color != ColorCache) {
        for (int i = 0; i < pWorld->count; i++) {
            auto& obj = pWorld->array[i];
            obj.r = Color.r;
            obj.g = Color.g;
            obj.b = Color.b;
        }
        ColorCache = Color;
    }

    return oModulateWorldColor(pWorld, a2); // Call trampoline
}

void InitHook() {
    MH_Initialize();
    MH_CreateHook((LPVOID)TargetAddress, &WorldModulation::hModulateWorldColor, (LPVOID*)&WorldModulation::oModulateWorldColor);
    MH_EnableHook((LPVOID)TargetAddress);
}
\end{lstlisting}

\section{Conclusion}

Trampoline hooking provides a stable and stealthy way to manipulate game logic without crashing the game or alerting anti-cheat systems. By preserving the return address and execution flow, it forms the backbone of our entire cheat architecture.

The process begins with reverse engineering target DLLs—most notably \texttt{client.dll}—to locate and understand the relevant functions. Then, byte-level patterns are extracted to scan and identify those functions reliably at runtime, enabling us to inject hooks safely and consistently. Finally, MinHook allows us to deploy trampoline hooks with minimal footprint, organized in clearly defined classes for maintainability.

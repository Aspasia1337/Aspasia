\chapter{Injection and Detection Techniques}

\section*{From Anti-Cheat Strategies to Injection Mechanisms}

In the preceding chapters, we examined the multifaceted approaches employed to combat cheating in online multiplayer games, encompassing technical, legal, and social strategies. Despite these efforts, cheat developers continually adapt, employing sophisticated methods to circumvent detection. A prevalent technique involves the injection of dynamic-link libraries (DLLs) into the game's process space, enabling unauthorized manipulation of game behavior.

This chapter delves into the technical intricacies of such injection methods, elucidating how they function and the challenges they pose to anti-cheat systems. By understanding these mechanisms, we can better appreciate the ongoing cat-and-mouse dynamic between cheat developers and game security measures.

\section{The Role of DLL Injection in Cheat Development}

In the realm of professional game cheating, particularly within competitive titles like \textit{Counter-Strike 2}, the injection of dynamic-link libraries (DLLs) into the game's process is a prevalent technique. This method allows unauthorized code to execute within the game's context, facilitating various forms of cheating.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Dynamic-Link Library (DLL)}} \\
A \textit{Dynamic-Link Library (DLL)} is a module containing functions and data that can be used by multiple programs simultaneously. In the context of game cheating, DLLs are injected into a game's process to modify its behavior at runtime, enabling functionalities not intended by the original developers \parencite{mitre2025dllinjection}.
\end{tcolorbox}

Injecting a DLL permits the cheat to operate concurrently with the game, granting the ability to:

\begin{itemize}
    \item \textbf{Hook game functions}: Altering or extending the behavior of existing game functions.
    \item \textbf{Modify memory}: Changing in-game variables such as player speed, ammunition count, or recoil patterns.
    \item \textbf{Read internal data}: Accessing sensitive information like player positions or health status.
    \item \textbf{Render overlays}: Displaying additional visuals (e.g., radar, ESP) directly onto the game screen.
    \item \textbf{Automate actions}: Executing tasks like aiming or firing without user input.
\end{itemize}

Due to the deep integration achieved through DLL injection, anti-cheat systems like \textbf{Valve Anti-Cheat (VAC)} prioritize detecting and preventing such unauthorized modifications to maintain game integrity.

\section{Overview of Code Injection Techniques}

Building upon the foundational understanding of DLL injection, it is imperative to explore the broader spectrum of code injection methodologies employed in cheat development. \textbf{Code injection} refers to the practice of introducing unauthorized code into a running process, thereby altering its behavior. In the context of game cheating, this often involves inserting a DLL or custom code into the game's memory space.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Code Injection}} \\
\textit{Code injection} is a technique whereby an attacker introduces malicious code into a vulnerable application, causing the application to execute unintended commands. This is typically achieved by exploiting inadequate input validation, allowing the attacker to manipulate the program's execution flow and potentially gain unauthorized access or control over the system \parencite{owasp2025codeinjection}.
\end{tcolorbox}

\subsection*{Traditional Methods}

Historically, cheat developers have leveraged standard Windows APIs to facilitate code injection. Two of the most prevalent functions are:

\begin{itemize}
    \item \texttt{LoadLibrary}: Loads a specified DLL into the address space of the calling process.
    \item \texttt{CreateRemoteThread}: Creates a thread that runs in the virtual address space of another process.
\end{itemize}

The conventional approach entails allocating memory within the target process, writing the path of the malicious DLL into this memory, and then invoking \texttt{CreateRemoteThread} to execute \texttt{LoadLibrary}, thereby loading the DLL into the target process \parencite{elastic2023injection}.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Classic DLL Injection Workflow}} \\
\textit{1.} Obtain a handle to the target process using \texttt{OpenProcess}. \\
\textit{2.} Allocate memory in the target process with \texttt{VirtualAllocEx}. \\
\textit{3.} Write the DLL path into the allocated memory via \texttt{WriteProcessMemory}. \\
\textit{4.} Retrieve the address of \texttt{LoadLibrary} using \texttt{GetProcAddress}. \\
\textit{5.} Create a remote thread in the target process to execute \texttt{LoadLibrary}, loading the DLL.
\end{tcolorbox}

While effective in earlier implementations, these methods have become increasingly detectable by modern anti-cheat systems due to their reliance on well-known API calls and the presence of the malicious DLL on disk. Consequently, cheat developers have evolved their techniques to employ more sophisticated and stealthy injection methods, which will be discussed in subsequent sections.

\subsection*{Manual Mapping: A Stealthier Injection Strategy}

As anti-cheat systems became more adept at detecting conventional injection methods, cheat developers responded with more sophisticated strategies. One such method is known as \textbf{Manual Mapping}, which remains a favored approach due to its stealth and flexibility.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Manual Mapping}} \\
\textit{Manual Mapping} is a technique in which a DLL is manually loaded into the memory space of a target process without invoking standard Windows loader functions like \texttt{LoadLibrary}. This bypasses many traditional detection mechanisms, as the injected module does not appear in the process's loaded module list and avoids creating suspicious threads \parencite{guidedhackingmanualmap, learnmmap2024}.
\end{tcolorbox}

Unlike traditional injection, Manual Mapping involves manually parsing the DLL's headers, resolving imports, handling relocations, and executing the entry point—steps that are normally handled by the operating system. This provides the attacker with full control over how and when the code is executed.

In particular, manual mapping enables:

\begin{itemize}
    \item \textbf{Avoidance of API hooks:} Since standard APIs are not called, API-based anti-cheat hooks are ineffective.
    \item \textbf{Concealed presence:} The DLL does not appear in module snapshots or standard tool output.
    \item \textbf{Flexible entry execution:} Control over when and how the DLL's code is run (e.g., hijacking existing threads).
\end{itemize}

\section{Detection Techniques in Anti-Cheat Systems}

Building upon the previously discussed injection methodologies, it is imperative to understand the countermeasures employed by modern anti-cheat systems to detect and mitigate unauthorized code execution. The techniques delineated in this section are not merely theoretical constructs; they are derived from meticulous reverse engineering of modules extracted directly from the game's memory during runtime. This analysis provides concrete evidence supporting the mechanisms and strategies outlined below.

Anti-cheat systems, such as Valve Anti-Cheat (VAC), deploy a multifaceted array of detection methods aimed at identifying anomalies indicative of cheating. These methods focus on uncovering abnormal memory modifications, unauthorized module injections, and manipulations of trusted system structures.

\subsection*{Thread Local Storage (TLS) Callbacks}

An initial opportunity for anti-cheat systems to detect injected code arises during the program's startup phase. Windows operating systems support the execution of special functions known as \textbf{Thread Local Storage (TLS) callbacks}, which are invoked automatically when a thread is created.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Thread Local Storage (TLS) Callback}} \\
A \textit{TLS callback} is a function that the Windows operating system automatically calls when a thread is created or terminated. These callbacks are typically used for initializing or cleaning up thread-specific data. However, they can also be leveraged by anti-cheat systems to perform early memory inspections before the main application code executes \parencite{mitre2025tls}.
\end{tcolorbox}

Anti-cheat mechanisms utilize this early execution stage to scan memory and inspect the runtime environment, often before the main game code begins. If an injected DLL includes TLS callbacks that are not properly removed or disabled, the cheat risks immediate detection during process initialization.

\subsection*{Start Address Integrity Checks}

Beyond startup checks, anti-cheat systems continuously monitor thread creation during gameplay. A common detection method involves verifying the \textbf{start address} of each thread.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Thread Start Address}} \\
The \textit{start address} is the memory location where a thread begins its execution. Legitimate threads typically start within official game modules, such as \texttt{client.dll} or other trusted libraries. Threads initiating from addresses outside these known modules are considered suspicious and may indicate injected code or shellcode execution \parencite{guidedhacking2023startaddress}.
\end{tcolorbox}

This method is particularly effective at detecting poorly concealed code injections or unauthorized shellcode executions.

\subsection*{Virtual Method Table (VMT) Hook Detection}

Another detection strategy focuses on the integrity of in-game objects. In object-oriented engines, game entities often utilize \textbf{Virtual Method Tables (VMTs)} to organize their functions.

\begin{tcolorbox}[colback=gray!10, colframe=gray!50, boxrule=0pt, sharp corners, width=\linewidth, left=1mm, right=1mm, top=0.5mm, bottom=0.5mm]
\makebox[\linewidth][c]{\textbf{Definition: Virtual Method Table (VMT)}} \\
A \textit{Virtual Method Table (VMT)} is a structure used in object-oriented programming to map object methods to their actual function addresses. By modifying a VMT, an attacker can alter how a game object behaves, enabling the hijacking of functions such as rendering or input handling \parencite{unknowncheats2024vmt}.
\end{tcolorbox}

Cheats often modify these tables to hijack behaviors. Anti-cheat systems can identify tampered VMTs by verifying:

\begin{itemize}
    \item Whether the VMT points to unexpected memory regions.
    \item Whether the methods referenced fall outside legitimate game or system modules.
\end{itemize}

\section{Extended VAC Capabilities and Developer Countermeasures}

Building upon the previously discussed detection methodologies, \textbf{Valve Anti-Cheat (VAC)} has evolved to incorporate a comprehensive suite of system-level monitoring techniques aimed at identifying and mitigating unauthorized code execution. These advancements extend beyond basic memory and thread inspections, encompassing a broader surveillance of the operating environment.

\newpage

\subsection*{Advanced Detection Mechanisms}

VAC's enhanced detection strategies include:

\begin{itemize}
    \item \textbf{File System Scanning}: VAC actively scans the file system for known cheat artifacts, such as specific file names, hashes, or signatures associated with cheating tools \parencite{valve2025vac}.
    \item \textbf{Process and Memory Inspection}: It inspects running processes for suspicious memory regions or injected modules that deviate from expected patterns \parencite{valve2025vac}.
    \item \textbf{Registry Monitoring}: VAC monitors the Windows registry for abnormal entries that may indicate the presence of persistent malware or cheat configurations \parencite{valve2025vac}.
    \item \textbf{Inter-Process Communication Tracking}: It tracks inter-process activity to detect unauthorized access or manipulation of the game process by external applications \parencite{valve2025vac}.
\end{itemize}

These multifaceted approaches enable VAC to construct a holistic view of system behavior, thereby enhancing its ability to detect sophisticated cheating mechanisms that may not be evident through isolated memory analysis.

\subsection*{Developer Countermeasures}

In response to VAC's advanced detection capabilities, cheat developers have devised a range of countermeasures aimed at evading detection:

\begin{itemize}
    \item \textbf{String Encryption}: Obfuscating identifiable patterns in memory by encrypting strings, making it more challenging for signature-based detection systems to recognize cheat-related code \parencite{glanz2020obfuscated}.
    \item \textbf{Name Randomization}: Dynamically changing module and window identifiers to avoid blacklisting and hinder heuristic analysis.
    \item \textbf{Polymorphic Code}: Employing self-modifying code that alters its structure upon each execution while preserving its functionality, thereby evading pattern recognition \parencite{morel2023polymorphic}.
    \item \textbf{Fileless Execution}: Operating entirely from memory without writing to disk, thus minimizing the forensic footprint and circumventing file-based detection mechanisms \parencite{crowdstrike2024fileless}.
\end{itemize}

These sophisticated evasion techniques exemplify the ongoing arms race between cheat developers and anti-cheat systems. As VAC continues to refine its detection methodologies, cheat developers correspondingly adapt their strategies to maintain operational stealth.

\subsection*{The Ongoing Arms Race}

The dynamic interplay between anti-cheat technologies and cheat development fosters a continuous cycle of innovation on both fronts. VAC's commitment to enhancing its detection capabilities is met with equally determined efforts by cheat developers to devise novel evasion tactics. This perpetual contest underscores the necessity for ongoing research and development in anti-cheat technologies to preserve the integrity of competitive gaming environments.
